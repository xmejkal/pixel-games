The output path:
- [★C2] MicroPython v1.29.0's `machine.I2S` is a thin shell over ESP-IDF `i2s_std`: Philips mode only, MCLK unused, no PDM and no TDM exposed. It moves bytes. It does not mix, loop, fade or resample · E ~/esp/micropython-v1.29.0/ports/esp32/machine_i2s.c:361-399 (FEAS-1, FEAS-2, FEAS-9) · caveat: the source was read, and no one ran it on this board
- [★C3] Buffer depth moves in 16 ms blocks at 16 kHz. Mono TX keeps a 2-byte DMA frame, so `ibuf` 2048 B is 4 blocks and 64 ms, and 4096 B is 8 blocks and 128 ms (calculated from 256 frames per block) · E ~/esp/micropython-v1.29.0/ports/esp32/machine_i2s.c:134-155 · caveat: re-read here. FEAS-3 reads mono as expanded to stereo, and the TX branch does not expand it. Not run on the board
- [★C4] The buffer that hides a stall delays every new sound. Events are polled once per frame (40 ms), so a hit waits up to 40 ms plus the buffer: about 104 ms with 64 ms of buffer and about 168 ms with 128 ms. Only the 128 ms buffer covers Road's 105 ms gap (calculated) · H calculated from ★C1, ★C3, FEAS-11, RA-5 · caveat: the 20 to 30 ms at which a delay is noticed is model knowledge (RA-5). Not measured on this board
- [★C5] The reports split on whether Python can fill samples one by one. The PO assistant says a naive version "cannot loop per sample" (RA-4, from 57 µs per particle and about 80 µs per canvas call, measured on other code). The tech lead calculates one voice at 16 kHz as 1.28 ms (2 µs per sample, a guess) to 6.4 ms (10 µs, an estimate) per 40 ms frame (FEAS-7). Fire leaves 17.6 ms of the frame, so one voice fits up to 27.5 µs per sample. The whole CPU is spent at 62.5 µs (calculated) · H EX-7, RA-4, FEAS-7, run130-p656-smoke.log:12 · caveat: no per-sample cost is measured on this board. The 17.6 ms comes from the means of one run
- [★C6] The Frame's "buffer underruns per minute" has no source in the stock class. ESP-IDF 5.5.2 offers `on_send_q_ovf` for TX, and the stock class sets it to NULL.
