- EX-6 · The frame has measured spikes. Fire: `fps 25 worst 48 slowest 38`, balls: `worst 57 slowest 40`, with a gc column of 2.0 and 3.0 ms average. `FRAME_MS = 40`. · E · run130-p656-smoke.log:12, 25, games/app.py:31 · supports only: the sizing of a sound buffer. - EX-7 · Python per-call cost is high on this board: about 80 µs of Python per canvas call (measured), 57 µs per particle per update. · E · docs/discovery/2026-11-03-engine/council/po-assistant.md PO-11, PO-12 (copied from bench.md, not re-read here) · supports only: that a naive Python version of sample generation cannot loop per sample. A "naive" version must be a Python control layer over a block-fill primitive, or it will underrun at once (H, from the numbers: 16000 samples/s at tens of µs each exceeds 1 s/s).

### Existing first: the platform (MicroPython and ESP-IDF)

- EX-8 · MicroPython's ESP32 `machine.I2S` is on the new ESP-IDF channel API (`driver/i2s_std.h`, `i2s_new_channel`, `I2S_STD_PHILIPS_SLOT_DEFAULT_CONFIG`). DMA frame length is fixed at 256 frames (`DMA_BUF_LEN_IN_I2S_FRAMES`), the DMA descriptor count comes from the `ibuf` argument. Non-blocking mode (callback) creates a FreeRTOS task pinned to `MP_TASK_COREID`, which is the MicroPython core. It has no underrun counter that I found in the file. · E · ports/esp32/machine_i2s.c lines 31, 45, 148-153, 363-377, 452-461 (fetched via gh api from micropython/micropython master, 2026-11-09) · supports only: that a stock `machine.I2S` plus a C fill function is the minimal path, and that the I2S task shares a core with the interpreter. Whether the pinned core matters for gc stalls is — (no measurement).
- EX-9 · The three modes of `machine.I2S` are blocking, non-blocking (callback, runs in the scheduler's context) and uasyncio (timeout=0 returns at once when there is no free DMA memory). Mike Teachman's example repo (MIT, last pushed 2025-01-26) is the maintainer's reference for them, and a bug report says the uasyncio example freezes on an ESP32-S3 once `drain()` stops returning. The docs give no word on underrun. · E · docs.micropython.org/en/v1.19/library/machine.I2S.html (search result summary, 2026-11-09), github.com/miketeachman/micropython-i2s-examples (gh api: MIT, pushed 2025-01-26), the issue #15340 page on notes.alelec.net (seen in a search result, not opened) · H for the freeze report (a forum thread; not reproduced) · supports only: that the callback path depends on the MicroPython scheduler, whose queue is 8 deep on the ESP32 (PO-23 of the engine council, from py/mpconfig.h). The callback is therefore a poor carrier for per-event sound, and fine as a "buffer is empty, refill" tick.
- EX-10 · The ESP32-S3 has two I2S peripherals; the S3's SIMD (PIE) set is small. A blog post lists missing operations including add and subtract without saturation. I found no esp-dsp routine for 16-bit saturating mixing. · E · docs.espressif.com/projects/esp-idf/en/v4.4.1/esp32s3/api-reference/peripherals/i2s.html (search summary), bitbanksoftware.blogspot.com/2024/01/surprise-esp32-s3-has-few-simd.html (search summary, 2026-11-09; page not opened) · H on the saturation claim (blog, not the TRM) · supports only: that "use the S3's special instructions" for mixing is unproven; mixing a few voices at 16 kHz needs far fewer than the 240 MHz core provides (H, no measurement). Where "S3 abilities" could matter is elsewhere: two I2S ports, the second core, PSRAM for samples (— whether the FireBeetle S3 board has it: not checked).

### Risks and assumptions

- RA-1 · Nobody is blocked now. The games run silently at 24 to 25 fps (measured), and no card lists a game waiting on sound. #160 round 3 and #875 mention sound as an option in the showcase, both as the PO's wish. The decider is the only user (n = 1). · E · run130-p656-smoke.log:12, issues 160 and 875 (read 2026-11-09), brief.md Start and reach · supports only: that the order is a choice; the value is the PO's own pleasure and the showcase (flag in brief: "shown in public as a showcase", H: P652 #875).
- RA-2 · What must be true, as I read the brief: (a) the DFR0954 plays I2S from the S3 board on pins that do not clash with the display's SPI and the two buttons (— not checked here); (b) stock `machine.I2S` can run beside a 40 ms frame loop without audible gaps; (c) a C fill function can be called from the I2S side without Python in the way; (d) fire and hit events are rich enough to drive a sound that the PO accepts as "realistic"; (e) the frame time of the games does not get worse (the brief's must-not-get-worse line). · H · my reading of brief.md Frame, EX-6, EX-8 · supports only: the list of beliefs to test.
- RA-3 · Riskiest belief (my proposal, the decider rates it): "Sound keeps playing without gaps while the games run at their worst frames (57 ms measured), without the sound hurting frame time". Why this one: the whole architecture (Python fills, C fills, own task, own driver) depends on where the stall comes from, and on one core the I2S task shares the core with the interpreter (EX-8). · H · EX-6, EX-8 · supports only: the choice of riskiest. Cheapest test: a probe file like the earlier `probeNNN.py` files on the board: start `machine.I2S` on the DFR0954 with `ibuf` for 100 ms, feed a 440 Hz tone from a `@native` or C block filler, run the fire game's frame loop with `gc.collect()` forced, and count gaps with a scope or by recording; the pass line is the decider's (before the run). No new C needed for the first probe: pure Python with a precomputed `array('h')` table loop-copied by `readinto`/`write` is enough (H).
- RA-4 · Second riskiest (my proposal): "A naive MicroPython version can be made without underruns at all". A per-sample Python loop at 16 kHz is not feasible from the call costs (EX-7). If the naive version underruns by design, the benchmark's first row shows "failed" for every metric, and the comparison of D2 compares nothing. Cheapest test: time `array`-based block generation of 256 samples of noise + exponential decay in plain Python on the board (10 lines, no C); if one block takes longer than its play time (16 ms at 16 kHz) the naive version needs a defined shape (for example a Python mixer over precomputed sample tables, no live synthesis). · H · EX-7 · supports only: that the "naive" must be defined before the benchmark. The brief's metric list has the underrun count already.
- RA-5 · Third (my proposal): "Physics events can drive sound in time". The event poll runs once per frame (40 ms). A hit heard 40 ms late is above the roughly 20 to 30 ms at which audio-visual delay is noticeable (H, model knowledge, not sourced here). Plus the display `send` is 3 to 5 ms and the DMA buffer adds its own length. Cheapest test: a bench probe that toggles a GPIO or plays a click at `hits` and measures the delay to the screen change with the phone video or a scope. · H · EX-5, EX-6 · supports only: that latency belongs in the benchmark beside the CPU time, which the brief's metric list does not include (— whether the PO wants it).
- RA-6 · Pre-mortem, "six months after sound shipped, it failed. Why?" Each cause with what points to it:
  1. The sound clicked and dropped out in the real games, since the buffer was sized on average frames, not on the gc stall or the display `send`. (H, EX-6: worst 57 ms against a typical 40 ms)
  2. The power rail dipped: a 3 W class-D amp at 5 V (or 3.3 V) from the FireBeetle pulling current beside the display backlight caused a brown-out, or noise on the I2S lines or on the ADC. The part record notes "3.3-5 V per DFRobot" but the board's supply and the speaker's rating are —. (H, EX-2)
  3. The naive Python version could not run, so the benchmark compared "does not work" with "works", and the pair behind one interface was never an honest pair. (H, RA-4)
  4. The C sound core grew its own design, the way two C layers grew in the engine pre-mortem (PO-30 item 4): `snd_` and `fx_` with different naming, because P609 #812 was still unsettled. (H, brief: "This card keeps its layout in step with P609 #812")
  5. A GPL library (arduino-audio-tools, ESP8266Audio) was copied in to hurry up the fire sound, and the MIT repository carried GPL-3.0 code. (H, table above; the engine council raised the same for Tiny Game Engine)
  6. The fire sound did not sound like fire and the PO stopped using it. "Realistic" has no pass line and no ear test. (H, the brief's outcome says "plays generated sound", no listening criterion)
  7. Sound was a demo that nobody heard: the showcase is shown on a laptop in a room without the speaker, or the speaker is too small for 3 W-class sound, and the loudness is —. (H, flag "shown in public as a showcase")
  8. The driver repository was created because `machine.I2S` seemed not enough, but the real limit was the frame loop, so a second submodule was kept alive for nothing. (H, brief diagram marks the driver "only if the discovery shows the need"; EX-8 shows stock I2S is C-fed possible)
  9. The S3 abilities named in the request (SIMD, second core) were never used, because the mixer's cost was already tiny; the "optimized" version won on nothing visible and the card's story did not show a gain (the engine council found the same for fps, PO-13). (H, EX-10)
- RA-7 · Backlog overlaps. #160 round 3 (sound over I2S with the DFR0954) is the same work seen from spark's walk, and its Done-when ("each round ends with the board doing the new thing and a logged bench verdict") differs from #997's ("a game plays sound, fire plays generated sound, one benchmark"). #812 (engine refactor, 21 sub-issues, 6 of 21 done) names Stepper vs World naming and a separate engine repository, so a new `snd_` file set lands in a core that is being renamed. #875 (showcase) lists "controls and sound" as an option after the games are demonstrable. #743 (graphics library P539) lists "uses each chip's special hardware" and the PO's note "maybe even the AI chip or instructions the S3 has", and it has open questions Q3 to Q9 (C or C++, fork or new repo) that a sound core also meets. · E · gh issue view 160, 812, 875, 743, 871 -R xmejkal/spark (2026-11-09) · supports only: that P729 has four parents' worth of constraints: layout (#812), showcase (#875), hardware path (#160), language choice (#743 Q4, still open?). Whether #743's Q4 and Q8 were answered since 2026-11-03 is — (not read).

## 3. Questions for the decider

- Is a GPL-3.0 dependency (arduino-audio-tools, ESP8266Audio) acceptable anywhere in the showcase, or MIT-compatible only? · decides: whether those two are libraries or inspiration only.
- What is the pass line for the riskiest test: no gap in how many minutes of play, at which sample rate and sample width? · decides: buffer size, whether stock `machine.I2S` is enough, and whether a driver repository is created (Q1 in the brief).
- Is output latency from the event to the sound a metric of the benchmark, beside CPU time, underruns, frame time and heap? · decides: the `bench.md` columns, and whether a Python-polled event is good enough.
- What does "realistic" fire sound mean as a test: your ear on the board, a recording compared, or "does not sound like noise"? · decides: whether the generator needs layers (hiss, crackle, ember pops) or one noise source with a filter.
- What shape is the "naive MicroPython" version: live per-sample synthesis, or Python control over precomputed tables or a block filler? · decides: whether D2's two versions are an honest pair (RA-4).
- Which prefix and layer names for the sound core (`snd_`, `fx_`, `audio_`), and does it wait for #812's naming? · decides: the file names in `engine/core/` and the cmake lines.
- Does the sound core use the second CPU core (own FreeRTOS task) when stock I2S pins its task to the MicroPython core? · decides: whether the core stays "plain C with no MicroPython and no RTOS" or takes an RTOS dependency.
