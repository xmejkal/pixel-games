# Tech lead: TECH (feasibility, direction) and PHYS (hardware numbers), P900

Read on 2026-11-18 in ~/Development/pixel-p900 (HEAD a4ae406) unless a pointer says otherwise. Nothing ran on a board. Tags: E pointer, H source, D who and when. "Calc" means I worked it out; the inputs are named with each number.

## Findings

### Memory: the bytes of a 96 px figure (TECH-1 to TECH-5)

- TECH-1 · Today's Rescue figures take 488,832 B in rescue.pak (all cycles, both facings, five kinds, 24 to 40 px wide). Rescue's pack is 660,008 B, of which the night street is 153,600 B. One fireman run picture is 26x30 px = 1,560 B. · E `games/art_index.py` ART rows for "rescue" (summed by calc: run 37,440, spray 28,800, turn 12,480, carry 43,200, carrykid 43,200, five people x run and wave 19,008 to 36,864 each); `games/art_index.py` PACKS "rescue" = 660,008 B; `ls -l games/packs/rescue.pak` · supports only: the baseline for scaling.
- TECH-2 · The pack format is raw RGB565, 2 B a pixel, one picture per pose per facing, in the panel's turned layout, with a key colour for transparency. There is no compression, no palette and no mirroring: the left poses are separate pictures, the exact mirror of the right ones, written at paint time. · E `art/export.py:14-27` (`to_bin`: 2 B a pixel, rotate 90), `art/sets/rescue.py:591-593` (`add` writes `ImageOps.mirror` pictures as `_l`), `games/pictures.py:20-33` · supports only: any size claim, and that facing doubles bytes.
- TECH-3 · The blit has no mirror or flip option: `blit_buffer(buf, x, y, w, h, alpha, key)` only. A mirrored pose needs a driver change in C, or a second picture. The driver source is the pixel-engine submodule, which is EMPTY in ~/Development/pixel-p900/engine (gitlink 1005249); I read the same commit in the sibling checkout ~/Development/pixel-master/engine (`git ls-tree` of p900 gives 1005249823e4d0f7..., the same id as pixel-master's `submodule status`). · E `~/Development/pixel-master/engine/driver/src/s3lcd.c:559-635`; `games/lcd.py:131-135` · supports only: the cost of the facings; not a claim that a C flag is small (not estimated).
- TECH-4 · Scaling Rescue's art by one factor k (picture bytes grow with k squared). The figure's own height is 26 px sole to helmet in a 30 px picture, so a 96 px figure is k = 96/26 = 3.69 and its run picture is 96x111 = 21,312 B (calc). Using k = 4 (the 24 px body height times 4) gives 104x120 = 24,960 B. Table of calc results, both facings, 12 poses a cycle unless noted (k = 3.69 · k = 4):
  - fireman run 511,488 · 599,040 B; spray (6 poses, 148x111 · 160x120) 394,272 · 460,800; turn (4 poses) 170,496 · 199,680; carry 591,408 · 691,200; carry-a-child the same again.
  - one person kind (run) about 504,096 · 589,824 B; a wave cycle the same again; a child about half (256,608 · 304,128 per cycle).
  - ALL of Rescue's figure cycles, scaled: 6,676,896 B (k 3.69) · 7,821,312 B (k 4). It cannot be a pack: the PSRAM is 8 MB and the pool, the frame and the heap share it (PHYS-1, PHYS-2).
  - a first-mission cut, two figures (fireman: run, spray; man: run, wave), both facings: 1,913,952 B (k 3.69) · 2,239,488 B (k 4). One facing only, if the driver could mirror: 956,976 · 1,119,744 B.
  - run only, two kinds, both facings: 1,015,584 · 1,188,864 B; as an 8-bit palette it would be half (not built; no 8-bit blit exists in the code I read).
  · E inputs: `art/sets/rescue.py:174` (FIG_H 26), `:181` (SIZES), `:530` (PEOPLE_SIZES), `games/art_index.py` (counts); the sum code ran in a scratch folder under $TMPDIR (deleted at the end) · calc; D2 gives "about 96 px", and "96 px tall" is not said to be the figure or the picture. If "96" meant the picture box (k = 3.2), the numbers fall by 25 % against k 3.69 (calc, not tabulated) · supports only: the size of the pool a first mission needs.
- TECH-5 · The biggest pack today is runner.pak, 739,216 B. The pool is made once at the first load as big as the largest pack and is never freed or grown without a hard reset. A first-mission pack of 1.9 to 2.2 MB would be 2.6 to 3.0 times the pool today and would hold that PSRAM for every game on the box. The first copy of a larger pack needs a hard reset. · E `games/pictures.py:42-52` (`block`), `~/Development/pixel-master/engine/driver/src/s3lcd.c:2917-2942` ("a larger size than the first raises ValueError"), `README.md:162-166` · supports only: the pool's growth cost.

### Time: drawing and sending 96 px figures (TECH-6 to TECH-9)

- TECH-6 · Drawing cost, from the repo's measured rows: a keyed 20x64 sprite takes 47.23 µs warm in the frame in PSRAM (36.9 ns a pixel, calc); a keyed 320x240 layer takes 6.86 ms (89 ns a pixel, calc). A 96x111 figure is 10,656 px, so 0.39 to 0.95 ms; a 148x111 spray 16,428 px, 0.61 to 1.46 ms; three figures 1.2 to 2.8 ms (calc, range from the two rows). Python's own cost of a `pictures.draw` call is 69 to 71 µs warm. · E `bench.md:196-217` (the P567 table, run46) · supports only: that the blit is not the frame's cost; no row measures a blit of this size on the board.
- TECH-7 · Sending: a full 320x240 frame is 31.0 ms at the real 40 MHz clock (calc check: 76,800 px x 16 bit / 40 MHz = 30.72 ms). A dirty rectangle costs about 0.46 µs a pixel plus a fixed cost (a 240x16 band 1.78 ms, one 16 px tile 0.35 ms). A 96x111 figure box, rounded out to 16 px tiles, is up to 112x128 = 14,336 px, so about 6.6 ms (calc); a spray box 164x128, about 9.7 ms. Three non-overlapping figures send about 20 ms (calc). The driver sends the tiles drawn this frame OR the last, so a figure that moves keeps its old tiles one more frame. Over 40 windows the driver sends the whole frame (31 ms). · E `bench.md:86` (31.0 ms), `bench.md:98-115` (tiles, windows, probe7 rows), `games/lcd.py:34,252` (PARTIAL True, WINDOWS) · supports only: the send estimate.
- TECH-8 · The frame model the plan and bench use: a frame costs the copy plus the larger of (step + paint) and the send, because `show()` copies windows to an internal buffer and returns. So 20 ms of figure send hides behind Rescue's paint of 27 to 33 ms; the figures do not set the rate unless paint falls below send. · E `bench.md:183-191`, `games/app.py:67` (FRAME_MS 40) · supports only: the model; "hides behind" is calc, not measured for figures.
- TECH-9 · The only Rescue numbers on the board are on its game-over screen, not in play: `time rescue step 5.9 paint 33.0 send 4.0 gc 7.2 fps 18 worst 150` and `step 8.4 paint 26.8 send 3.7 gc 7.5 fps 19 worst 84`; the avg line says `static 16.4 paint 14.5`. P846 says idle games sat on their game-over screens. No row has Rescue in play with six figures. · E `logs/run-p846-baseline-a.log:85-92`, `bench.md:1640-1657` · supports only: that Rescue was under the 40 ms pace (18 to 20 fps) before any larger figure; "frame time of the new game" is H.

### Load time (TECH-10)

- TECH-10 · Rescue's pack load: README says 548 ms on 2026-11-14; the only kept log says `load 638 ms` (2026-11-16, P846, the P822 loader, `switch rescue 1428 ms`). I found no log with 548. Rates: 660,008 B / 0.548 s = 1.20 MB/s; / 0.638 s = 1.03 MB/s (calc). A 1.9 to 2.2 MB first-mission pack at those rates takes 1.6 to 2.2 s (calc), 2.5 to 4 times Rescue's. Before the pack file existed the old per-file load of 1,507,152 B took 2,154 ms (0.7 MB/s). The loader reads 8,192 B chunks (about 6 ms) so sound and the loading card keep running. · E `README.md:383`, `logs/run-p846-baseline-a.log:84`, `bench.md:214` (the 2,154 ms row), `games/pictures.py:23-24,72` · supports only: the load estimate; the two Rescue numbers disagree (see What I could not check).

### Hardware numbers (PHYS)

- PHYS-1 · PSRAM: 8 MB octal on the owner's board (DFR0975 N16R8: 16 MB flash, 8 MB octal PSRAM). 8 MB = 8,388,608 B. The ESP-IDF reported 8.32 MB free in its heap before the pool. Provenance: stated (board record), stated (bench), datasheet-typ not given. Pointers: `~/Development/spark/boards/firebeetle2-esp32s3.json:9` ("DFR0975 is the N16R8 (16 MB flash, 8 MB octal PSRAM)"); `bench.md:174` ("8.32 MB free there, `esp32.idf_heap_info`"); Espressif ESP32-S3-WROOM-1 datasheet v1.1 line "Flash up to 16 MB, PSRAM up to 8 MB" (sha256 bc430d66...b76b in the store). The datasheet's ECC option would cut usable PSRAM by 1/16; no ECC setting was found in the artefacts, so I assume off (H).
- PHYS-2 · What is free of it, measured on the board: after a 1,507,152 B art set and the frame, "PSRAM free 6,747,500 B, largest block 6,553,600 B; gc free 6,603,376 B", and a 4,000,000 B bytearray allocated (`bench.md:214`, P567, 2026-11-02 era, "double" run, measured). Free heap at boot differs by document and build: 7,432,720 B (v1.22.2, `bench.md:21`), 8,319,680 B (stock v1.29, `bench.md:28`), 8,053,120 B (`_engine` build, `bench.md:1688-1692`, P849), `mem 7954816` (P846 log line 3). All measured; they are different builds and moments, so they do not contradict, but no row says the free heap with a pool of 2 MB. How they relate: MicroPython v1.29 starts a 64 KB heap and grows it in areas from malloc (PSRAM) (`~/esp/micropython-v1.29.0/ports/esp32/mpconfigport.h:30-36,89-90`, `main.c:133-142`), and `s3lcd.pool` is a `heap_caps_malloc(..., MALLOC_CAP_SPIRAM)` taken once. So pool, frame (153,600 B), `engine` objects and the Python heap draw on one PSRAM of about 8.3 MB (H from those pointers; the measurement 6.75 MB free is consistent: 8.32 - 1.51 - 0.15 = 6.66 MB, calc). A 2 MB pool leaves about 6.2 MB (calc) for heap, sound bank (README; the fire bank is 246,960 B, box bank 443,222 B) and the frame.
- PHYS-3 · Internal RAM: 512 KB SRAM on the chip (datasheet v2.2: "SRAM: 512 KB"); internal largest block 188,416 B after the run (measured, `bench.md:214`). The Python heap holds 77 to 86 KB in a game (`bench.md:175`); the stock build keeps 32 KB internal in reserve (`sdkconfig` of the build clone: `CONFIG_SPIRAM_MALLOC_RESERVE_INTERNAL=32768`, `ALWAYSINTERNAL=8192`). Figures are in PSRAM, not here. · E as given; the sdkconfig is a build artefact in `~/esp/micropython-v1.29.0/ports/esp32/build-ESP32_GENERIC_S3-SPIRAM_OCT/sdkconfig:1549-1563,1589-1592`, which may be from another build than the flashed one (not checked).
- PHYS-4 · CPU and PSRAM clock: 240 MHz CPU, PSRAM 80 MHz (octal) in that build's sdkconfig (same file, lines 1549 and 1592); the datasheet says the PSRAM maximum clock frequency is at least 80 MHz (Table 5-12, datasheet v2.2, "FC Maximum clock frequency 80 MHz" in the Min column). I did not read a CPU clock from a log of the flashed box. Provenance: build config (stated), datasheet-min.
- PHYS-5 · Screen bus: SPI, 4-line, to an ST7789V2 panel in a DFR0664 module over the GDI cable (SCK 17, MOSI 15, DC 3, CS 18, RST 38, BL 21). The code asks for 60 MHz; the S3 divides 80 MHz by 2 and runs at a real 40 MHz (bench reading: 60 MHz takes 63 ms and the wire needs 31 ms, "fits a real clock of 40 MHz"). 80 MHz showed a dark screen. The datasheet minimum serial write cycle is 16 ns (62.5 MHz max), with 390 ohm series resistors on the module (stated, unverified in the record). Time for a full frame: 76,800 px x 16 bit / 40 MHz = 30.72 ms (calc) against 31.0 ms measured. Dirty figure send: see TECH-7. Provenance: datasheet-min (16 ns), measured (31.0 ms, dark at 80), calc. Pointers: `games/app.py:73-76` (SPI_HZ 60_000_000, "the panel's write cycle limit is 16 ns, 62.5 MHz"), `bench.md:34-36,86`, ST7789V2 datasheet Version 1.0, 2016/11, section 7.4.3 (4-line serial), table row TSCYCW "Serial clock cycle (Write) 16 ns" min, PDF page 44, file sha256 8937678475e20598c8deb17c3cdd41403da6317a3b6518f86144b8a609de9f46 (in the store), and the shelf record `~/.local/share/spark/shelf/dfr0664-tft-2in.json` fact `series_resistors_ohm` (390, schematic V0.1, `verified: false`).
- PHYS-6 · Two documents differ on a number each: (a) Rescue's load, README `README.md:383` "548 ms" (2026-11-14, no log kept) against `logs/run-p846-baseline-a.log:84` "load 638 ms" (2026-11-16); (b) the framebuffer cost of a full-frame blit: bench's "blit_buffer of a full 240x320 picture from PSRAM 2.65 ms" (`bench.md:171`, run35, before P556) against 6.83 ms in the "double" mode (`bench.md:196-205`, run46) and the note "4.25 ms more into PSRAM".
