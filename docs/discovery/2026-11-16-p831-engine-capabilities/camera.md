# P831: the camera and an edge AI model on the game box (a preliminary note)

Spike P831 ([#1192](https://github.com/xmejkal/spark/issues/1192)). Written 2026-11-16 from sources only. Nothing was run on a board and no model was downloaded.

> **TL;DR.** The box already has the camera hardware: the DFR0975 carries an OV2640 on a DVP connector, and the ESP32-S3 can run small int8 vision models in the 50 to 130 ms range. It is feasible, but it is a firmware project first (the image has no camera driver and no inference engine) and a pin project second (the camera takes 5 pads the box uses today). The smallest thing that works is no AI at all: a motion or "where is the bright blob" reading from a 96x96 grey picture, computed in C, that moves a paddle.

In three sentences. The camera could give the games a body-as-controller (a face or hand position, motion), a selfie in a game picture, or a "somebody is there" wake-up. Capture runs on the chip's own DMA in a background task and inference runs in C on the chip's vector unit, so the game's 40 ms frame only needs to read the newest result. The cost is a rebuilt firmware (the camera driver, then an inference engine), a new C module, and giving up the joystick, the amplifier shutdown and the microphone clock pads, which the camera uses.

## 1. What the camera could do for the games

| Idea | Needs | Size of the job |
|---|---|---|
| Motion / "the bright blob is at x" as a controller (paddle follows a hand or a torch) | grey 96x96, frame difference in C | smallest: no model, no download |
| Presence ("somebody is in front of the box": wake the screen, start attract mode) | a person-detection model (VWW, 250 KB) | small |
| Face position as controller (lean left, right) | a face detector, centre of the box | medium |
| Selfie into a game picture (the face as a sprite in the pool) | a RGB565 capture, crop, blit | small in code, big in pool memory |
| Hand pose, gestures | a hand model; none was sourced here | large, skip for now |

Smallest that works: motion as controller. Next: face position as controller, because it is the first thing that needs a model.

## 2. The hardware (sourced)

- The board's page says "Onboard OV2640 (2MP, 68 degrees FOV)", the interface "CAM" is DVP, "compatible with OV2640 and OV7725" ([DFRobot wiki, DFR0975](https://wiki.dfrobot.com/SKU_DFR0975_FireBeetle_2_Board_ESP32_S3), read 2026-11-16). The drawer lists the DFR0975 as "with Camera", count 3, all used; it does not say how many of the three have the camera fitted. That needs a look at each board. The drawer also holds two FIT0672 camera extension cables (for Raspberry Pi cameras; not checked if they fit this connector).
- The camera's AVDD, DVDD and DOVDD come from an AXP313A power chip that the firmware must enable first, over I2C on GPIO 1 and 2 (same wiki page). The chip's I2C address and register were not sourced.
- Camera pins (same wiki): SDA 1, SCL 2, VSYNC 6, HREF 42, PCLK 5, XMCLK 45, D2 39, D3 40, D4 41, D5 4, D6 7, D7 8, D8 46, D9 48.

### Pin clash with the box (read from games/pins.py)

| Camera pin | Pad | The box uses it for |
|---|---|---|
| 4 (D5) | A0 | JOY_X |
| 5 (PCLK) | A1 | JOY_Y |
| 6 (VSYNC) | A2 | AUDIO_SHUTDOWN (the amplifier) |
| 7 (D6) | D5 | JOY_SW |
| 8 (D7) | A3 | MIC_SCK |

No clash with the ST7789 display (SCLK 17, MOSI 15, CS 18, RST 38, BL 21, SD_CS 9), the I2S speaker (12, 13, 14), the encoder (43, 44) or the on-board button (47). So display and speaker keep working. The joystick, the amplifier's shutdown pin and the microphone clock lose their pads. The speaker's shutdown could be tied on in hardware (the amplifier stays on); the joystick and the microphone cannot both stay. The pin map is generated by spark's assign_pins.py, so the camera is a new part record and a new requirements file, not a hand edit.

## 3. The chain

```
OV2640 --DVP/I2S-parallel--> esp32-camera driver (DMA, PSRAM frame buffers, fb_count 2, grab LATEST)
   -> crop/resize to 96x96 grey (or 120x160 RGB) -> int8 model (ESP-NN / ESP-DL on the S3 vector unit)
   -> result {x, y, score} in a small struct -> the game reads it each 40 ms frame
```

Industry names: capture = [esp32-camera](https://github.com/espressif/esp32-camera) (Apache-2.0; ESP32-S3 supported; OV2640 and OV3660 among 17 sensors; formats JPEG, RGB565, YUV422, grey; it warns that RGB/YUV into PSRAM is slow and can drop data, especially with Wi-Fi on). Preprocess = resize and normalise. Inference = TensorFlow Lite Micro with ESP-NN kernels ([esp-tflite-micro](https://github.com/espressif/esp-tflite-micro), Apache-2.0) or [ESP-DL](https://github.com/espressif/esp-dl) through [ESP-WHO](https://github.com/espressif/esp-who) (face, pedestrian, QR detection; ESP-IDF 5.4 to 6.1; its licence was not stated on the page read).

## 4. What runs in C and what in Python

- C, always: capture (driver task), resize/convert, inference, frame difference. Python cannot do per-pixel work at this size in 40 ms (the engine already keeps its pixel loops in C for the same reason).
- Python: start/stop, the knobs (resolution, threshold), and reading the result: one call that returns a few numbers. The game never touches the picture, except the selfie idea, which hands a buffer to the engine's blit.
- The camera module of [cnadler86/micropython-camera-API](https://github.com/cnadler86/micropython-camera-API) (read 2026-11-16; MicroPython 1.24 or newer, ESP-IDF 5.2 or newer recommended; the box builds 1.29.0 on IDF 5.5.2) gives `capture()` (a memoryview), `frame_available()`, `reconfigure()`, S3 defaults of fb_count 2 and LATEST. It covers capture only, not inference.
- Inference in MicroPython: no maintained binding was found. The closest is [mocleiri/tensorflow-micropython-examples](https://github.com/mocleiri/tensorflow-micropython-examples) (microlite, a user C module; old, state for 1.29 unknown). The honest path is a thin C module of our own around esp-tflite-micro, in the engine/ submodule, with a Python call that returns the result.

## 5. Frame time and memory

Numbers are from the sources, on ESP32-S3 at 240 MHz, not measured on this box.

| What | Time | Source |
|---|---|---|
| Capture OV2640 QVGA RGB565 / grey | about 12.5 fps (80 ms a frame) | cnadler86 README benchmark, fb=1, xclk 20 MHz |
| Capture QVGA JPEG | 25 fps (50 with fb=2) | same |
| Person detection (VWW, int8), `invoke()` | 54 ms with ESP-NN (2300 ms without); 47 ms in internal RAM | [esp-nn README](https://github.com/espressif/esp-nn) |
| Face detect, two-stage MSR (120x160) + MNP (48x48) | 32.5 ms + 5.9 ms per candidate | [ESP-DL human_face_detect README](https://github.com/espressif/esp-dl/blob/master/models/human_face_detect/README.md) |
| Face detect, one stage 224x224 | 129.4 ms (and 7.3 ms preprocess) | same |
| Pedestrian detect pico_s8_v1, 224x224 | 113.3 ms (10.6 preprocess) | [ESP-DL pedestrian_detect README](https://github.com/espressif/esp-dl/blob/master/models/pedestrian_detect/README.md) |

Reading: one inference is 1.5 to 3 game frames, and capture alone is about 2 frames. So camera and model run in their own task, at 8 to 12 results a second, and the game reads the newest one each frame. It cannot be inside the 40 ms frame (FRAME_MS in games/app.py). The open cost is the shared PSRAM bus: the display framebuffer (240x320 RGB565 = 153,600 bytes) and the picture pool already live in PSRAM ("double" framebuffer), and a QVGA RGB565 capture is another 153,600 bytes written per frame, twice with fb_count 2. 8 MB PSRAM holds that easily; the bandwidth and the cache are the risk, not the size. A grey 96x96 model input is 9,216 bytes. The tensor arena of the 250 KB person model was not sourced (the TFLM page gives only "250 kilobyte").

Flash: 16 MB holds a 250 KB model and a few hundred KB for ESP-DL models many times over. The firmware app partition of the MicroPython 16 MB layout was not checked here.

## 6. The firmware build it needs

The box builds MicroPython v1.29.0, BOARD=ESP32_GENERIC_S3, BOARD_VARIANT=SPIRAM_OCT, ESP-IDF v5.5.2, with `USER_C_MODULES` (build.sh, micropython.cmake). Adding the camera means:

1. Add the esp32-camera component (an `idf_component.yml` entry, as the cnadler86 README says) and its `micropython.cmake` to `USER_C_MODULES`; `CONFIG_CAMERA_PSRAM_DMA` for the S3 (named on the esp32-camera page). The default build has no camera.
2. For inference, add esp-tflite-micro (ESP-NN on by default on the S3), then our own binding.
3. A rebuild, a new image and a deploy, with the engine and s3lcd as today. The image grows by the driver and the kernels. Its size was not measured.
4. A camera init that first enables the AXP313A over I2C, then starts the driver with the pins of section 2.

ESP-IDF 5.5.2 is inside the support list of ESP-WHO (5.4 to 6.1) and of esp-tflite-micro (5.1 to 6.0), so no IDF change is needed. The one-tool-per-job rule fits: one camera driver, one inference engine.

## 7. The smallest first experiment

Steps. (1) Look at which of the three boards has the OV2640 fitted. (2) Rebuild with the camera module only. (3) Free A0..A3 and D5 (no joystick, no mic, shutdown tied on), generate the pin map with the camera. (4) Enable AXP313A, init at QQVGA grey, `capture()` in a loop beside the running game. (5) In C, difference two frames and return the x of the biggest change.

It measures: capture fps with the game running; the game's frame time and tear with the camera on and off (does the PSRAM bus starve the display send?); heap and PSRAM used; the time of the frame difference; whether the result moves a paddle with a hand, in a lit room. Pass: the game keeps 40 ms frames and the paddle follows. Then step two: the ESP-DL face detector, measured on the box against the table above.

## 8. Risks

- Pins: five pads lost (section 2). A shared board cannot keep joystick and camera.
- PSRAM: octal PSRAM at 80 MHz serves the display, the pool and the capture at once; the driver warns of lost data when writing RGB to PSRAM, worst with Wi-Fi on (ESP-NOW for two boards, the other P831 option, uses the radio).
- Power: the camera comes from the AXP313A and the box runs from USB or a 1S LiPo; the camera's current was not sourced. Measure.
- Licences: esp32-camera, esp-tflite-micro and esp-nn are Apache-2.0 (spark is MIT; Apache-2.0 is compatible, and spark never commits vendor files, so the components are fetched at build). A Hugging Face model needs its licence read: [EclipseAidge/mobilenet_v1_vww](https://huggingface.co/EclipseAidge/mobilenet_v1_vww) states none, is ONNX not TFLite, 96x96 RGB; Silicon Labs' [MLTK MobileNetV1 VWW](https://siliconlabs.github.io/mltk/docs/python_api/models/tinyml/visual_wake_words.html) is about 334 KB, float, 96x96x3. A model must be converted to int8 and tested; Espressif's own models ship in ESP-DL.
- Privacy: a camera in a game box films the room. The first rule is that the picture never leaves the chip.
- Heat: the cnadler86 README warns the OV5640 can overheat; the OV2640 was not flagged.
- Edge Impulse ([ESP32 page](https://docs.edgeimpulse.com/hardware/boards/espressif-esp32)) was tested on a DFRobot FireBeetle, but delivers a C++ library for ESP-IDF, no MicroPython, and its free-plan terms were not found. It breaks "free, few and local" if it needs an account; skip.

## 9. What it would add to the engine, for the games

A `Sensor` seam: one small C class that runs a capture task and a model task and exposes `latest()` (a few numbers and an age in ms). Games read it like they read the buttons (a new input kind beside `Buttons` and the encoder), so a game does not know a camera exists. It would also expose `snapshot()` into the picture pool for the selfie. The same seam could hold the microphone later (keyword spotting), which is why the shape should not say "camera".

## 10. Open decisions for the PO (recommended answer first)

1. Which board gets the camera? Recommend one of the three, rebuilt for it, and a second pin map; do not mix with the joystick box.
2. First goal? Recommend motion as controller (no model); then a face detector. Not hand gestures.
3. Model source? Recommend Espressif's own (ESP-DL, ESP-WHO) and the TFLM person model, not an arbitrary Hugging Face model; read each licence first.
4. Order against ESP-NOW and the synthesizer? The camera is the biggest firmware change and takes the most pads; recommend it after ESP-NOW. This is for the options page to settle.
5. May the camera and Wi-Fi run together? Recommend no for the first experiment.

## Could not source

The AXP313A address and the camera's current; a release version for cnadler86's module and for esp-who; ESP-WHO's licence text; the size of the ESP-DL models and the tensor arena; a Hugging Face int8 TFLite person model; any measured fps for ESP-WHO on an S3 (only per-model latency from the READMEs); the app partition size and the image growth.
