### B. Measured costs that D3 rests on

- **PO-11** · Python physics is expensive on this board: 57 µs per particle and 114 µs per spring body per update (measured). 40 particles alone take 2.27 ms. 30 bodies and 40 particles take 5.69 ms (measured). `Bodies.step` over a full pool allocates 544 B per call, `Spring.step` 112 B (measured, floats boxed). In RENT's lost rounds the slowest frame took up to 60 ms, 15 ms of it the physics step (measured). · E · bench.md P567 table rows "Python physics", origin/p582-heavy bench.md P582 bullets "Allocation" and "After (run51)" · supports only: that moving the step into C has a measured cost to remove. The average fps did not drop (24.03, 24.00 fps), so the gain shows in worst frames and in headroom, not in average fps.
- **PO-12** · A canvas call is mostly Python, not C: about 98 µs per call all in, of which about 8 µs is C (measured, runner). After the lean cut, about 80 µs of Python per call remains. An empty call costs 2.10 µs in a loop, 5.5 µs measured elsewhere. · E · bench.md:154-163 (P550) · supports only: that a binding which is called many times per frame (per body, per attribute) pays tens of µs per call in Python. A C core helps only if Python crosses into C a few times per frame, not per object.
- **PO-13** · The fps outcome cannot show a gain for stack. `FRAME_MS = 40` paces every frame, so the ceiling is 25 fps (calculated: 1000 ms / 40 ms). Stack already runs at 24.00 to 24.09 fps (measured). The brief's "no lower fps than today" is a regression gate only. · E · games/app.py:26, 164-174, bench.md P568 "Before" 24.09 fps, origin/p582-heavy bench.md run 52 24.00 fps · supports only: that the engine's benefit must be observed in the `time` line's step ms, the worst gap or a heavier scene, not in fps.
- **PO-14** · The Mac tests import the game code as plain Python, with `tests/stubs` for `framebuf` and a `fast.native` that is a no-op. On p582-heavy, `tests/test_stack.py` tests `Pile`, `pile_under` and the collapse on the Mac (42 tests reported OK on #783). · E · games/fast.py:1-7, `origin/p582-heavy:tests/test_stack.py` lines 1-20, #783 comment "42 tests OK" · supports only: that physics moved into C either needs a Python twin, a host build of the C, or loses these Mac tests.

### D. Risks and assumptions

- **PO-24** · Nobody is blocked by the engine today. (a) RENT #783: slices 1 to 3 were built in Python on motion.py and ran at 24.00 fps (measured). The PO's material decisions (tip by centre of weight, rigid pivot, thud, 3 lives) are rules a Python step can express. (c) Restyle #769: waits on effects in C (P583 #784), not on the engine. · E · #783 comments of 2026-11-03, #786 body, #784 "Needed by", PO-11 · H for (a)'s rule fit (my reading of the decisions) · supports only: that the engine's order is a choice, not forced by a blocked card.
- **PO-25** · The physics feel changed four times in one day, each after the PO played: S1 spring press, S2 cut-off slabs, S3 throw, then rigid tip and pivot with lives. Each change was code, not a parameter. · E · #783 comments of 2026-11-03 ("This replaces the cut-off slabs of S2", "This replaces the S1 spring press and the S3 throw", "Play goes on, a life lost") · supports only: that the feel loop is the fastest-changing part of the game. If that loop moves into C, every change pays a firmware build and a flash. Build-and-flash time per iteration is —.
- **PO-26** · The C layer has three claimants with one design asked: the engine (D3), the graphics library P539 (its Q4 on C17 against C++17 and Q8 on the fork against a new repository are still queued), and effects P583. #787 says "keep the two in step, one design". · E · docs/discovery/2026-11-02-graphics-library/brief.md:159-164 (Q3 to Q9 queued), #743 comment "Still open: Q3 to Q9", #787 Notes · supports only: that D3's design cannot fix the C layer's language, repository or layer shape without answering, or explicitly deferring, P539's Q4 and Q8.
- **PO-27** · WIP is already over the limit the PO set. Build holds P469 #637, P511 #706 and P582 #783, and #771 needed a WIP exception. An engine build adds to a stage that is full. · E · #783 comment "Build holds P469 #637, P511 #706 and this card", #771 comment "WIP exception", CLAUDE.local.md board limits (2 per working stage) · supports only: a sequencing risk, not a design risk.
- **PO-28** · Riskiest assumption (my proposal): "The game's feel can be tuned from Python while the step runs in C". D3 pays off only if the C core is a stable mechanism (integrate, collide, rest, report) and every feel decision (what a landing does, when a floor tips, what a life costs) stays a Python reaction or a Python-passed number. PO-25 shows the feel changes daily. PO-6 shows the PO already accepted "numbers from Python, never constants in C" for effects. · H · my reading of PO-25, PO-6, p580-finding.md:77 ("Gravity, drag and speeds are passed in from Python on every call, never constants in C") · supports only: the choice of riskiest assumption. Its cheapest test is a paper replay: classify each of #783's four feel changes as "C mechanism change" or "Python reaction or parameter" under a draft engine API. If two or more need a C change, the split is wrong. No board needed.
- **PO-29** · Second-riskiest (my proposal): "Few crossings per frame". A C core pays off only if Python crosses into C a few times per frame (one step, one event read, one draw batch). A per-object binding (properties per body, a callback per contact as in PO-15) brings back the about 80 µs Python cost per call of PO-12. Cheapest test: a board probe that times one C `step()` over 12 bodies plus a poll of a 16-entry event buffer, against today's Python `Bodies.step`, and against 12 property reads from Python. · H · PO-12, PO-15, PO-23 · supports only: that the binding's grain is a design decision with a measurable cost.
- **PO-30** · Pre-mortem, "six months after the engine shipped, it failed". Most likely causes, each with what points to it:
  1. The feel loop moved into C. Each of the PO's play notes needed a rebuild and flash, the loop slowed from same-session to next-day, and RENT never reached "heavy and natural". (H, PO-25)
  2. The engine was designed ahead of the games. A general rigid-body solver (a Box2D or Physac port) took the epic's time: stacking stability at a 40 ms step and a dt clamped at 60 ms (gfx.py:326) became the rabbit hole. The refuter already found two floors releasing at once at 60 ms frames (#783, SHOULD 2). (H, PO-22, #783 refuter re-check)
  3. Half the games were ported and half were not, so two APIs lived side by side and every fix was made twice. (H, model knowledge of migrations)
  4. Two C layers grew: the engine's and P539's library, with different naming and layer rules, because P539's Q4 and Q8 were never answered. (H, PO-26)
  5. The Mac tests stopped covering physics, and regressions were found only on the board. (H, PO-14)
  6. The value never showed: fps stayed at the 24 to 25 fps pace ceiling, so the PO saw cost and no gain. (E, PO-13)
  7. C called Python per contact during a collapse, which allocated and raised the worst gap above today's 70 ms (measured, run 52). (H, PO-15, PO-23)
  8. GPL code from the Tiny Game Engine entered the MIT repository by copy. (H, PO-15)

## 2. What I did not check, and why

- Build-and-flash time per C iteration: the build logs (build-*.log) hold no timings I read, and no bench entry times a full cycle. This number decides how much PO-25 and PO-28 matter.
- Whether a rigid pivot topple for 11 floors fits the frame in Python: no prototype exists. Only the drop, the throw and the pile are measured.
- The per-call cost of a C-to-Python method call (`mp_call_method_n_kw`) on this board: not measured. The probe in PO-29 measures it.
- Thumby Color's frame rate under physics, and the cost of its synchronous callbacks: not found, not searched.
- Whether Physac, Chipmunk2D or Box2D builds as a MicroPython user module for xtensa-esp32s3 and how much RAM a 12-body scene takes: no source found. Box2D v3's SIMD paths and their scalar fallback were not read.
- The status review artifact (claude.ai/artifact/WP3FkD3DX1MwwvSVyV9Frq) named in #787: not read, to stay inside the time box. Its claims reach me only through #785 and #788.
- The council files of the P539 and P565 discoveries beyond the lines cited: not reread. I cite their briefs and do not redo them.
- 32blit and PicoSystem internals for physics or events: not read (licence and description only).
